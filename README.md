# Live Trading Bot Reliability

**一个自动化交易系统跑起来不难，难的是你睡着的时候它别出事。**

*Reliability lessons for AI-coded / vibe-coded trading bots. 无策略、无收益数据，只讲工程。*

如果你用 Cursor、Claude Code、ChatGPT 这类 AI 工具写过一个自动交易脚本——它已经能跑，甚至开始挂真钱——这个仓库是写给你的。

## 60 秒看到第一个坑：假绿灯

```bash
python examples/false_green_light.py
```

你会看到同一个任务，两种判据给出**相反**的结论：

```
【场景一】AI 典型写法（吞异常 + rm -f 收尾）
  日志最后一行 : 任务执行成功
  退出码       : 0

  判据 A：看退出码  →  rc = 0  →  判定：成功 ✅
  判据 B：看痕迹    →  产物文件不存在 —— 任务实际上没有执行
                                  →  判定：失败 ❌

  >>> 两个判据结论相反。真相是：任务根本没执行。
```

这不是刻意构造的 bug。运行脚本、看输出、翻源码里的注释，只要一分钟。

## 自动交易系统的失效方式，和你想的不一样

大多数人的假设是：「监控会说，程序挂了会告警」。

| 你以为 | 实际会发生的 |
|---|---|
| 程序挂了会有告警 | **监控脚本自己也会挂，而且没人知道** |
| 任务成功会显示 Success | **包装脚本最后一条是 `rm -f`，所以永远返回成功** |
| 告警响了说明有问题 | **告警响了，但消息根本没送到** |
| 面板没显示持仓 = 没有持仓 | **也可能是数据源断了** |

## AI 生成代码的四个高发失效模式

这是本仓库认为最值得单独说的部分：AI 写出来的可靠性代码，失效方式有明显的聚集区。每一条都来自真实踩坑。

| AI 的高发写法 | 为什么危险 | 一句话对策 |
|---|---|---|
| `except Exception: pass` | 错误彻底消失——不崩、不报、日志里都没有 | 异常必须落日志或触发告警，二选一 |
| 乐观日志：「已发送」「任务完成」 | 记录的是"调用过"，不是"发生了" | 日志只写**验证过**的事实 |
| 包装脚本以 `rm -f` 收尾 | 清理命令几乎永远成功 → 退出码永远 0 → 假绿灯 | 关键命令的退出码不能被覆盖；最终以验证产物收尾 |
| 加守护进程但不说盲区 | 每一层守护自己也会挂，AI 不会主动告诉你 | 显式写下"防线停在第几层、那一层的盲区是什么" |

> 单独看，每一条都无害，甚至算"最佳实践"。组合起来，会让你的整个监控体系变成装饰品。

## 五条最值钱的教训

### 1. 「假绿灯」：任务日志里的 Success 可能是假的

一个定时任务，日志显示执行成功。但检查实际的运行痕迹，什么都没发生。

**原因**：包装脚本的最后一条命令是 `rm -f`（清理临时文件）。这条命令几乎必然成功 —— **所以整个脚本的返回码永远是 0**。

> **判据：不要看任务的退出码，要看它应该产生的痕迹。**
> 日志有没有新增？文件有没有更新？时间戳变了吗？

### 2. 「不知道 ≠ 没有」：监控面板的三态设计

一个显示持仓的面板，在数据源断开时显示"无持仓"。

**这是个危险的谎言** —— "没有持仓"和"不知道有没有持仓"是完全不同的状态，但在界面上长得一样。

**正确做法**：任何监控指标必须有**三态**：

| 状态 | 显示 |
|---|---|
| 有值 | 显示数值 |
| 值是 0 | 显示 `0` |
| 取不到值 | 显示 `未获取` / `N/A`（**不能用 0 代替**） |

### 3. 告警链路必须端到端验证

「告警响了」和「消息送到了」是两件事。

真实的失败模式：
- 推送服务的 token 过期 → 发送失败，但本地日志显示"已发送"
- 网络问题 → 请求超时，异常被吞掉
- 消息被平台限流 → 静默丢弃

> **验证方法：主动发一条测试消息，确认收到。**
> 不是检查代码有没有调用发送函数，是确认**手机真的响了**。

### 4. 守护进程自己也会挂

设计了一个守护进程去监控主进程。但**守护进程自己挂了，谁来管？**

这是一个无限递归问题，实际的做法是：

| 层级 | 机制 |
|---|---|
| 主进程 | 被守护进程监控 |
| 守护进程 | **写心跳文件** |
| 外部检查 | 读心跳文件，超时则告警 |

**但最后一层仍然有个洞**：如果外部检查自己也停了，还是没人知道。

> **诚实的结论：这是一个可以无限加深的问题，必须在某一层停下来，并明确知道"停在哪里"、"那一层的盲区是什么"。**

### 5. 日志归档，不要截断

日志文件涨到限制大小时，两种处理：

| 做法 | 后果 |
|---|---|
| ❌ 截断（保留最后 N 行） | **历史丢失** —— 出问题时要查的那段正好被删了 |
| ✅ 归档（保留历史文件） | 占用磁盘，但可追溯 |

> **磁盘很便宜，事后无法追溯很贵。**

## 防线设计（七层）

```
第一层  进程存活          交易进程死了 → 推送告警
第二层  守护进程          监控挂了 → 自动拉起
第三层  心跳机制          上报进程卡死 → 超时自动重启
第四层  面板服务          面板挂了 → 自动拉起
第五层  日志管理          涨到上限 → 归档保留历史
第六层  守护自监控        守护停了 → 读心跳推告警
第七层  数据源健康        实时源无效 → 回退 + 探针验证
```

**每一层都对应一个真实发生过的失效。**

详细设计见 [docs/defenses.md](docs/defenses.md)。
