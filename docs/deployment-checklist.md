# 部署检查清单：三步法，缺一不可

**部署完之后，大部分人会检查"任务配好了没"。
但真正出事的地方，往往在另外两步。**

---

## 三步法

```
① 任务配置对不对        —— 你配的东西，是不是你想配的
② 文件在不在            —— 它引用的文件，真的存在吗
③ 运行痕迹对不对        —— 它真的跑了吗，跑出了什么
```

**三步缺任何一步，都不算部署完成。**

---

## 第一步：任务配置

### 检查什么

- [ ] 执行时间（cron 表达式）正确吗？
- [ ] 执行用户正确吗？（**路径权限问题常源于此**）
- [ ] 工作目录正确吗？（**相对路径依赖这个**）
- [ ] 环境变量齐全吗？
- [ ] 命令的绝对路径写对了吗？

### 常见错误

| 错误 | 表现 |
|---|---|
| 用相对路径 | 手动跑可以，cron 跑失败 |
| 环境变量缺失 | 手动跑可以，cron 跑失败 |
| 用户不对 | 权限拒绝，或写到错误的目录 |

> **"手动能跑，定时不行" 的九成原因是这两个：工作目录和环境变量。**

---

## 第二步：文件在不在

### 检查什么

**按完整路径 Read 一次。** 不要假设。

```bash
# 不是 ls 目录，是确认这个具体文件
test -f /full/path/to/script.sh && echo "存在" || echo "不存在"
```

### 为什么单独列一步

因为**配置看起来完全正确，但引用的文件不存在** ——
这是一个非常常见的状态，而且不会在配置阶段暴露。

### 额外的检查

- [ ] 脚本有执行权限吗？（`chmod +x`）
- [ ] 脚本里的换行符正确吗？（**Windows 编辑的文件在 Linux 上会因 `\r` 失败**）
- [ ] 引用的解释器路径存在吗？（`#!/bin/bash` vs `#!/usr/bin/env bash`）

---

## 第三步：运行痕迹

### 检查什么

**不要看退出码。**

> **定时任务日志里的 `Successful` 可能是假象** ——
> 如果包装脚本的最后一条是清理命令（如 `rm -f`），
> **它几乎必然成功，所以整个脚本永远返回 0。**

### 应该检查的痕迹

```
□ 日志文件有新增内容吗？
□ 目标输出文件的时间戳更新了吗？
□ 数据库有新的记录吗？
□ 应该产生的中间文件存在吗？
```

### 具体做法

```bash
# 记录部署前的状态
BEFORE=$(stat -c %Y /path/to/output.log)

# 等一次调度周期

# 检查是否变化
AFTER=$(stat -c %Y /path/to/output.log)
if [ "$BEFORE" = "$AFTER" ]; then
    echo "❌ 文件未更新，任务可能没真正执行"
fi
```

## 一个完整的部署验收模板

```markdown
## 部署验收记录

### ① 任务配置
- 调度：<cron 表达式>
- 执行用户：<用户>
- 工作目录：<路径>
- 命令：<完整命令>

### ② 文件检查
- [ ] 主脚本存在且可执行：<路径>  → 验证结果
- [ ] 依赖文件存在：<路径>  → 验证结果
- [ ] 权限正确  → 验证结果

### ③ 运行痕迹
- 部署前日志行数：<N>
- 部署前输出文件 mtime：<时间>
- ——— 等待一个调度周期 ———
- 部署后日志行数：<N>
- 部署后输出文件 mtime：<时间>
- 结论：✅ 有变化 / ❌ 无变化

### 异常情况
<如有，记录>
```

## 补充：首次部署时容易漏的

- [ ] **测试告警通道** —— 主动触发一次，确认收到
- [ ] **回滚方案** —— 出问题怎么退回上一版？
- [ ] **备份** —— 覆盖前先备份（**已交付的文件不覆盖，新建带日期的版本**）
- [ ] **记录部署时间** —— 便于后续排查

---

## 一句话

> **"配置正确"不等于"部署成功"。
> 要看到它真的跑了，并留下痕迹，才算数。**
