# 可观测性：三态设计、告警链路、心跳

**"系统在正常运行"和"你以为系统在正常运行"，是两个不同的东西。**

---

## 一、三态设计（最重要的一条）

### 问题

大多数监控只区分两种状态：正常 / 异常。

**但实际需要三种。**

一个真实场景：面板显示"当前持仓：无"。

这句话可能意味着两件事：

1. **确实没有持仓**（正常）
2. **数据源断了，取不到**（严重问题）

**但两者在界面上长得一模一样。**

### 正确做法

| 状态 | 显示 | 颜色建议 |
|---|---|---|
| 有值 | 具体数值 | 正常 |
| 真的是 0 / 空 | `0` / `—` | 正常 |
| **取不到** | **`未获取`** | **警示色** |

### 应用范围

这条原则适用于**所有**监控指标：

```
进程状态   运行中 / 已停止 / 未获取
数据更新   正常 / 延迟 / 未获取
持仓数量   有值 / 0 / 未获取
账户余额   有值 / 0 / 未获取
网络延迟   有值 / — / 未获取
```

### 为什么这条重要

> **用 0 表示"取不到"，会让一个故障伪装成正常状态。**

这是最危险的一类 bug —— 它不报错，测试也发现不了，
只有在真正出事的时候才暴露。

## 二、告警链路

### 「响了」和「送到了」的区别

```
触发条件  →  生成告警  →  调用发送  →  送达  →  你看到
   ①            ②            ③        ④       ⑤
```

**任何一环断掉，你都收不到告警。**
但代码里看起来"发送成功了"——因为 ③ 返回了。

### 各环节的失败模式

| 环节 | 失败模式 |
|---|---|
| ① 触发 | 阈值设错，从不触发 |
| ② 生成 | 消息格式错误 |
| ③ 调用 | Token 过期、网络超时、异常被吞 |
| ④ 送达 | 平台限流、静默丢弃 |
| ⑤ 看到 | 消息被其他内容淹没 |

### 修法

#### 1. 发送失败必须记录

```python
try:
    r = 发送(消息)
    if r.status_code != 200:
        log.error(f"告警发送失败: {r.status_code} {r.text}")
except Exception as e:
    log.error(f"告警发送异常: {e}")     # 不要静默吞掉
```

#### 2. 端到端验证

**定期主动发一条测试消息，确认手机真的响了。**

不是检查代码，是**验证结果**。

> **判据：你亲眼看到消息到达，才算这条通道可用。**

#### 3. 重要性分级

| 级别 | 通道 |
|---|---|
| 一般信息 | 单一通道 |
| 重要告警 | 主通道 + 备用通道 |
| 严重故障 | 多通道 + 重复提醒 |

## 三、心跳机制

### 解决的问题

**进程存在 ≠ 进程在工作。**

一个进程可能：
- 死锁，卡在某个等待上
- 陷入无限循环
- 在等待一个永远不返回的网络请求

**这些情况下，`pgrep` 都显示"进程存在"。**

### 做法

```python
# 被监控进程：定期写心跳
def heartbeat_loop():
    while True:
        with open(HEARTBEAT_FILE, 'w') as f:
            f.write(str(int(time.time())))
        time.sleep(30)
```

```bash
# 外部检查：心跳是否过期
LAST=$(cat /path/heartbeat 2>/dev/null || echo 0)
NOW=$(date +%s)
if [ $((NOW - LAST)) -gt 900 ]; then
    echo "心跳超时，进程可能卡死"
    # 告警 + 重启
fi
```

### 阈值选择

**必须大于最长的正常单次执行时间。**

| 阈值 | 后果 |
|---|---|
| 太小 | 正常任务被误杀 |
| 太大 | 卡死很久才发现 |

**建议**：设为正常最长执行时间的 **2–3 倍**。

### 心跳文件本身也可能出问题

| 问题 | 表现 |
|---|---|
| 文件不存在 | 首次运行 |
| 文件内容损坏 | 读取失败 |
| 时间戳在未来 | 系统时钟问题 |

**修法**：读取失败时按"未知"处理（三态原则），不要直接当成"正常"。

## 四、可观测性的三条原则

### 1. 三态：有值 / 零 / 未获取

不要用 0 表示"取不到"。

### 2. 可验证：加了的检查要能证明它在工作

主动制造故障，确认告警到达。

### 3. 显式降级：所有降级都要产生信号

静默降级比崩溃更危险 —— 崩溃你知道，降级你不知道。

---

## 五、一个诚实的边界说明

**完全的可观测性是不存在的。**

举例：如果监控系统自己挂了，且没有任何外部观察者，你就无法知道。

**实际做法是分层，并明确每层的盲区：**

| 层 | 监控什么 | 盲区 |
|---|---|---|
| 应用层 | 业务逻辑 | 应用进程本身 |
| 进程层 | 进程存活 | 监控进程自己 |
| 系统层 | 心跳文件 | 检查脚本自己 |
| **外部** | — | **（需要独立机器/人工）** |

> **不要假装已经全覆盖。明确写下"盲区在哪"，比假装没有盲区更安全。**
