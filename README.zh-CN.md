# Live Trading Bot Reliability

[English](README.md) · **中文**

> 一个自动化交易系统跑起来不难，难的是你睡着的时候它别出事。
>
> *Reliability lessons for AI-coded / vibe-coded trading bots. 无策略、无收益数据，只讲工程。*

---

## 1. 这是什么

一份诚实、简短的实战手册（外加一个可运行的复现示例）：写给用 AI 搭了个自动交易 bot、现在需要确认"自己睡觉的时候它还活着"的人。

它首先写给**不会编程、但高强度用 AI 干活的人**：如果你的交易脚本已经能跑、甚至开始挂真钱，这个仓库就是写给你的。专业量化 / SRE 工程师可以直接把七层防线设计和部署清单拿去用。

## 2. 为什么需要它 —— 结论放在最前面

**先说答案**：bot 几乎不是"崩掉"的，而是**静默**掉的 —— 进程没了、进程卡住了、或者告警根本没送到 —— 而你能看到的所有界面都显示一切正常。策略部分已经做完了；"发现这种静默"的那部分，没人写。

大多数人的假设是：「监控会说，程序挂了会告警」。实际会发生的是：

| 你以为 | 实际会发生的 |
|---|---|
| 程序挂了会有告警 | **监控脚本自己也会挂，而且没人知道** |
| 任务成功会显示 Success | **这个 Success 可能是假的 —— 任务根本没跑** |
| 告警响了说明有问题 | **告警响了，但消息根本没送到** |
| 面板没显示持仓 = 没有持仓 | **也可能是数据源断了** |

上面每一行，都来自一套真实运行的系统 —— 第 4 节讲每一条长什么样、怎么防。

## 3. 怎么用

### 跑一遍自己确认 —— 一条命令，无密钥、无网络

```bash
python examples/false_green_light.py
```

Python 3，只用标准库 —— 不用装任何东西，不需要密钥，不联网。它把证据写在旁边的 `examples/state/` 目录里，每次运行都会自动重置；这个目录随时可以删。

它会让同一个任务给出**两种相反的结论**：

```
【场景一】AI 典型写法（吞异常 + rm -f 收尾）
  日志最后一行 : 任务执行成功
  退出码       : 0

  判据 A：看退出码  →  rc = 0  →  判定：成功 ✅
  判据 B：看痕迹    →  产物文件不存在 —— 任务实际上没有执行
                                  →  判定：失败 ❌

  >>> 两个判据结论相反。真相是：任务根本没执行。
```

（脚本输出是中文；上面这几行就是你会看到的内容。）这不是刻意构造的 bug —— 跑一遍、看一眼源码注释，一分钟。

## 4. 五条最值钱的教训

下面这五条，是本仓库认为最值钱的；也正是它们，让 AI 写的可靠性代码不是随机出错，而是聚集在几个固定写法上。这张表是索引，**每一节只补充表格没讲的东西：判据、怎么做、真实场景、代价。**

| AI 的高发写法 | 为什么危险 | 一句话对策 |
|---|---|---|
| `except Exception: pass` | 错误彻底消失——不崩、不报、日志里都没有 | 异常必须落日志或触发告警，二选一 |
| 乐观日志：「已发送」「任务完成」 | 记录的是"调用过"，不是"发生了" | 日志只写**验证过**的事实 |
| 包装脚本以 `rm -f` 收尾 | 清理命令几乎永远成功 → 退出码永远 0 → 假绿灯 | 关键命令的退出码不能被覆盖；最终以验证产物收尾 |
| 加守护进程但不说盲区 | 每一层守护自己也会挂，AI 不会主动告诉你 | 显式写下"防线停在第几层、那一层的盲区是什么" |

> 单独看，每一条都无害，甚至算"最佳实践"。组合起来，会让你的整个监控体系变成装饰品。

### 教训 1 —— 「假绿灯」：任务日志里的 Success 可能是假的

**发生了什么。** 一个定时任务，日志显示执行成功。但它本该留下的运行痕迹，不在。

**判据。** 不要看任务的退出码，要看它应该产生的痕迹：日志有没有新增？文件的时间戳变了吗？数据库里有没有新行？

**代价。** 你会在"一切正常"的错觉里过好几周。这是整份清单里最贵的一个失效，因为它从任何角度看都不像有问题。

### 教训 2 —— 「不知道 ≠ 没有」：监控面板的三态设计

**发生了什么。** 数据源断开时，一个显示持仓的面板显示"无持仓"。**「没有持仓」和「不知道有没有持仓」在界面上长得一模一样 —— 而你可能会据此做决策。**

**做法。** 任何监控指标必须有**三态**，而不是两态：

| 状态 | 显示 |
|---|---|
| 有值 | 显示数值 |
| 值是 0 | 显示 `0` |
| 取不到值 | 显示 `未获取` / `N/A`（**不能用 0 代替**） |

**代价。** 用 0 表示"取不到"，会让故障伪装成正常状态 —— 这是最危险的一类 bug：它不报错，测试也发现不了，只有在真正出事之后才暴露。

### 教训 3 —— 告警链路必须端到端验证

**发生了什么。** 本地日志显示"告警已发送"。手机没响。

**为什么。** 链路上任何一环断掉，你都收不到：触发 → 生成告警 → 调用发送 → 送达 → 你看到 —— 而代码依然看起来没问题，因为中间那一步返回了。真实的失败模式：推送凭证过期，而日志还写着"已发送"；网络超时，异常被吞掉；消息被平台限流，静默丢弃。

**判据。** 主动发一条测试消息，确认收到 —— 不是检查代码有没有调用发送函数，是确认**手机真的响了**。

### 教训 4 —— 守护进程自己也会挂

**发生了什么。** 你设计了一个守护进程去监控主进程。但谁来管守护进程？

**做法。** 这是一个无限递归问题，唯一诚实的做法是在某一层主动停下来：

| 层级 | 机制 |
|---|---|
| 主进程 | 被守护进程监控 |
| 守护进程 | **写心跳文件** |
| 外部检查 | 读心跳文件，超时则告警 |

**但最外层仍然有个洞**：如果外部检查自己也停了，还是没人知道。

> 诚实的结论：这是一个可以无限加深的问题，必须在某一层停下来，并明确知道"停在哪里"、"那一层的盲区是什么"。不要假装已经全覆盖。

### 教训 5 —— 日志归档，不要截断

**发生了什么。** 日志文件涨到限制大小，等出问题去查，需要的那段已经不在了。

| 做法 | 后果 |
|---|---|
| ❌ 截断（保留最后 N 行） | **历史丢失** —— 出问题时要查的那段正好被删了 |
| ✅ 归档（保留历史文件） | 占用磁盘，但可追溯 |

> 磁盘很便宜，事后无法追溯很贵。

## 5. 防线地图

```
第一层  进程存活          交易进程死了 → 推送告警
第二层  守护进程          监控挂了 → 自动拉起
第三层  心跳机制          上报进程卡死 → 超时自动重启
第四层  面板服务          面板挂了 → 自动拉起
第五层  日志管理          涨到上限 → 归档保留历史
第六层  守护自监控        守护停了 → 读心跳推告警
第七层  数据源健康        实时源无效 → 回退 + 探针验证
```

**每一层都对应一个真实发生过的失效。** 完整设计、取舍，以及照抄之前值得先知道的两个坑（第二层的竞态、第三层的阈值），都在 [`docs/defenses.md`](docs/defenses.md)。

**七层背后有一条通用原则：**「我加了这个检查」不等于「这个检查在工作」—— 每一层都要靠一次主动制造的故障来证明自己。

有两件事留在 `docs/` 里，不在本文重复：数据源健康层（怎么区分"数据源失效"和"市场没波动"、为什么回退必须响、探针该返回哪些状态），见 [`docs/observability.md`](docs/observability.md)；部署三步（配置、引用的文件、真实运行的痕迹），见 [`docs/deployment-checklist.md`](docs/deployment-checklist.md)。

## 6. 边界与不适用

本仓库**刻意不包含**：

- 任何策略逻辑、交易参数、品种信息
- 任何收益数据、实盘表现
- 任何交易所名称、账户信息

来源系统的所有策略细节已脱敏。**这个仓库的价值不在"什么策略能赚钱"，而在"怎么让你写的系统在你睡觉的时候别静默死掉"。**

必须先说清的诚实边界：

- **完全的可观测性不存在。** 最外层永远留着它的盲区（见教训 4），本仓库也不会消掉它。如果监控系统自己挂了、且没有任何外部观察者，你就是无法知道。
- **这些教训来自一套真实运行中的自动化交易系统**（已脱敏）—— 是一份实战报告加一份清单，不是行业标准。
- **这不是一个可以直接安装的监控产品。** 它交付的是文档和一个可运行的示例，不是能塞进你 bot 的库。这里的一切都需要按你自己的进程名、路径、调度器、告警通道改造。
- **它不适用于想要策略或收益的人。** 这里没有任何关于 alpha 的内容。如果你的自动化一直有人盯着跑，那么其中几层（守护进程、心跳、自监控）解决的是你目前还没有的问题。

**一个判断"这仓库适不适合你"的实用判据**：你现在能不能立刻答出，你的 bot 是否活着、以及它的告警是否真的能送到你手上？如果第二条你不确定，从教训 3 开始。
